# Flow 迭代效率复盘 — 贴纸重构 8 轮迭代评估

> 日期：2026-08-28
> 范围：RFC-001 Flow 驱动贴纸系统重构方案的 8 轮迭代（v1–v7 需求）
> 结论：**方向合理（文档驱动 + 严格审查），但执行效率偏低，理想 2–3 轮可完成，实际 8 轮属低效放大。**

## 二、效率数据

- **总轮次**：8 轮（7 次暂存 + 1 次通过）
- **总耗时**：纯运行约 2 小时+，含人工生成需求与监控约数小时
- **Token 消耗**：单轮 Coder 最高约 13 万 tokens；Document Admin 单轮最高约 **110 万 tokens**（MCP/Git 工具来回占大头）
- **收敛内容**：从“文档骨架”逐步收敛到“实现级细节”，最终方案与第 1 轮方向一致，无质变

## 三、合理之处

1. **失败报告闭环**：每轮 Reviewer 的 P0/P1 逐条写入下一轮需求，无遗漏，最终方案完整、可直接作为实现蓝图。
2. **文档驱动**：先冻结架构与契约再写代码，避免实现期大规模返工。
3. **稳定性加固有效**：600s 超时、指数退避重试、上下文截断、遥测关闭，解决了真实环境故障，使第 8 轮能稳定跑完。

## 四、低效原因分析

| 问题 | 表现 | 根因 |
|---|---|---|
| 审查标准漂移 | 前几轮 P2、错别字、章节编号也被当作拒绝理由 | 未在第一轮固定 P0/P1/P2 分级与“P2 不阻塞”口径 |
| 需求手抄循环 | v2–v7 全靠人工把失败报告抄进需求 | 缺少“失败报告 → 新需求”的自动化模板 |
| 确定性小事进循环 | 错别字、版本号、编号、MIME 白名单条目各耗一整轮 | 未用 lint/脚本/静态检查先行过滤 |
| Document Admin token 失控 | 单轮最高 110 万 tokens | MCP/Git 工具反复调用，无调用次数与 token 预算限制 |
| 一轮混审多层 | 架构、契约、代码补丁在同一轮被同时审查 | 未做分层审查，问题逐层显现导致多轮 |

## 五、未来改进方向

### 5.1 流程层面

1. **标准一次到位**：第一轮即在需求中固定 P0/P1/P2 分级，明确“P2 及以下不影响合入”，杜绝标准漂移。
2. **分层审查**：按 架构 → 契约 → 代码补丁 → 实现细节 分轮审查，每轮只审一层，避免混在一起反复打回。
3. **自动生成下轮需求**：由脚本从失败报告提取 P0/P1 并生成 vN+1 需求，减少手抄与遗漏。

### 5.2 工程层面

4. **确定性检查前置**：错别字、版本号、章节编号、MIME 白名单等用 lint/脚本/CI 静态检查，不进入 LLM 审查循环。
5. **限制 Document Admin 开销**：限制 MCP 工具调用次数、设置 token 预算；文档同步类任务交给人工或轻量脚本。
6. **审查输入截断策略**：Reviewer 只接收与当前审查层相关的章节，而非整份文档，降低超时与成本。

### 5.3 治理层面

7. **建立迭代上限与仲裁**：同一任务连续 N 轮未通过时自动进入人工仲裁，而不是无限生成新需求重跑。
8. **记录每轮成本**：将 token 消耗、耗时、失败原因纳入失败报告，作为是否继续自动迭代的决策依据。

## 六、结论

- 8 轮迭代虽然最终产出了高质量、可实施的方案，但**效率不理想**：核心方向在第 1 轮已确定，后续 7 轮主要消耗在标准漂移、需求手抄、确定性小事与 Document Admin token 浪费上。
- 按上述改进，同类任务预计可收敛到 **2–3 轮**（1 轮架构 + 1 轮契约/安全 + 1 轮代码补丁收口）。
- 后续贴纸实现与其它重构任务应直接采用“分层审查 + 标准固定 + 自动生成需求 + 预算控制”的新流程。
