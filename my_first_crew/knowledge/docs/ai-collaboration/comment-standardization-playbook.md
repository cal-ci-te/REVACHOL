# 注释规范化工程 · 作业手册

> 日期：2026-09-13
> 范围：REVACHOL 全仓注释规范化（批次 1~7），供后续 AI 执行同类任务时参照
> 结论：**方法可复用，但真正的风险不在"写注释"，而在"只改注释"这个承诺本身**——
> 整体重写会悄悄改动末尾换行、行尾空白、文件编码；工具本身也可能是错的。
> 本文记录的全部坑都来自实战，每条附现象、根因与对策。

---

## 一、规范是什么

依据 `knowledge/docs/development/code-style.md`。

### 1.1 三层结构

1. **模块头**：文件顶部第一行固定为 `// ！<模块定位>`（Python / Shell / YAML 用 `# ！`），
   后接 1–3 行说明模块是什么、为什么存在。
2. **成员标签**：函数 / 类 / 常量上方，动宾短语 ≤12 字，不加句末标点。
3. **决策理由**：贴近关键代码。有取舍时写 `选择 A 而非 B：<理由>`；
   有约束或坑时写 `<做法>：<后果或约束>`。

一行写不下就换行续写，不要写超长行，**也不要用行尾注释**。

### 1.2 只写为什么

只解释「为什么这样做」与「约束」，不复述「代码做了什么」。
自检方法：**若没有这条注释，读者会不会卡住或改错？不会就不写**。

这条是判断注释价值的唯一标准，也是后面「测试文件为什么只做减法」的依据。

### 1.3 硬性约束

| 约束 | 说明 |
|---|---|
| 只用行注释 | `//` 或 `#`；禁止 `/* */`、`/** */`、JSDoc |
| 中文 | 注释一律中文（命令示例、代码片段的英文可保留） |
| 禁止分隔线 | 如 `// ============`、`# ===== 标题 =====` |
| 禁止过程标记 | `[MODIFIED]`、`[DEPLOY]`、`[FUTURE]`、「改动 1」、`@author`、版本记录 |
| 禁止行尾注释 | 见 §六.6 的唯一例外 |
| 零信息丢失 | 原文中有效的取舍说明、约束、路径格式、单位必须保留 |

## 二、不可违背的三条底线

做这类任务最容易翻车的地方不是注释质量，而是这三条：

### 2.1 底线一：代码行为必须绝对不变

**验证方式不是肉眼比对，而是机器校验**——见 §四。

一次性发现过 6 处**预先存在**的缺陷（缺 import 导致 `ReferenceError`），
它们与注释无关，但正因如此才必须证明「不是我改出来的」：
拿基线提交（本例 `a059952`）回验，确认缺陷早已存在。

### 2.2 底线二：除注释外，一个字节都不能动

这是最容易被忽视、也最难保证的一条。以下都会在「整体重写」时被静默改变：

- **文件末尾换行**：19 个文件曾被补上末尾换行（详见 §六.2）
- **行尾空白**：大量空白行带缩进，重写即抹平
- **文件编码与 BOM**：4 个文件带 UTF-8 BOM，`utf-8` 写入会抹掉 BOM（详见 §六.8）
- **引号风格 / 字符串转义**：`"\x1b"` 这类字面量经多层转义后可能被"顺手规范化"

对策见 §六.1~.2、§三.3。

### 2.3 底线三：不确定就问，不要替用户决定

以下决策**必须**先问，因为它们改变任务边界：

- 文档字符串（docstring）算注释还是代码？（§六.3）
- 测试文件要不要套用完整三层？（§六.12）
- 发现死配置 / 孤儿脚本，删还是标注？（§六.11）
- 文件格式本身是否支持注释？（§六.9）

## 三、标准作业流程

### 3.1 侦察（动手前必做）

1. **枚举文件与规模**：按目录统计文件数、行数、文件类型。
2. **按格式判定注释可行性**——不能只按扩展名想当然：

   | 格式 | 可行 | 注释前缀 |
   |---|---|---|
   | `.js` / `.mjs` | ✓ | `//` |
   | `.cjs` | ✓ | `//` |
   | `.py` | ✓ | `#`（docstring 另论，见 §六.3） |
   | `.sh` | ✓ | `#` |
   | `.yml` | ✓ | `#` |
   | `Dockerfile` | ✓ | `#` |
   | `.jsonc` | ✓ | `//` |
   | **`.json`** | **✗ 语法不支持** | — |
   | 无扩展名（如 `.prettierrc`） | 看内容，通常是 JSON | — |

3. **筛查异常**：BOM、非 UTF-8 编码、0 字节文件、生成物（`package-lock.json`）。
4. **摸清注释现状**：有多少分隔线、装饰性注释、行尾注释，哪些文件完全无注释。
5. **试点 1 个文件**验证整条链路，再铺开。

### 3.2 建工具链并**证明它有效**

工具建好不等于可信。必须做反证测试：

- 故意改代码 → 工具应报 FAIL
- 只加注释 → 工具应报 PASS
- 无改动 → 工具不应误报

工具若"永远 PASS"，等于没有校验。

### 3.3 逐文件改写：优先"逐行定位替换"，慎用整体重写

| 方式 | 适用 | 风险 |
|---|---|---|
| **逐行/整段替换**（按行号定位注释行） | 含行尾空白、BOM、特殊字面量的文件 | 低。代码字节零改动 |
| 整体重写 | 无行尾空白、无 BOM 的干净文件 | 高。需额外校正末尾换行与空白 |

用整体重写时，**改完必须比对**：末尾换行状态、行尾空白行数与内容，都应与基线一致。

### 3.4 每批校验后立即提交

单批规模控制在 20~30 文件，保证可审阅、可局部回滚。
提交信息用 Conventional Commits，`style(<scope>)`，正文写明改了哪几类注释、
**并声明"零代码行为变更 + 校验通过"**。

发现代码缺陷要**另开 `fix` 提交**，绝不混入 `style`。

## 四、校验工具链

位于 `scripts/comment-audit/`，均为自研零依赖（JS 侧用 `acorn`）。

| 工具 | 用途 | 用法 |
|---|---|---|
| `codecmp.mjs` | JS/CJS 的 **token 级**等价校验（比 HEAD 与工作区） | `node codecmp.mjs <files...>` / `--staged` |
| `codecmp_py.py` | Python 的 **AST 级**等价校验 | `python3 codecmp_py.py <files...>` / `--staged` |
| `audit.mjs` | 注释规范审查 + 导入完整性检查 | `node audit.mjs <files...>` / `--imports` / `--all` |
| `trailing_check.py` | Python 行尾注释检测（基于 `tokenize`） | `python3 trailing_check.py <files...>` |
| `move_trailing.py` | 行尾注释转前置（批量、保真） | `python3 move_trailing.py [--apply] <files...>` |

### 4.1 为什么 JS 用 token、Python 用 AST

- JS：`acorn` 分词后丢弃注释与空白，比较 token 序列。注释改动后序列必然完全相同。
- Python：标准库 `ast.dump(..., include_attributes=False)` 比较语法树，
  天然忽略注释与格式差异。

两者都**不比较文本**，所以换行、缩进、空行、注释格式的差异不会造成误报，
而任何代码改动都会导致失败。

### 4.2 等价校验之外还要核对的三件事

等价校验查不出"非注释改动"，必须手工补三项：

```bash
# 1) 末尾换行：与基线逐文件比对最后一个字节
# 2) 行尾空白：比对"行尾带空白的行"的数量与内容
# 3) diff 删除行：只允许删掉注释行
git diff -U0 <files> | grep -E "^-[^-]" | grep -v "^\-\-\-" | grep -vE "^-\s*(//|\*|/\*|#)"
# 期望无输出；有输出说明删除了代码行，需人工确认是否为"行尾注释改前置"
```

第三项的**合理例外**：把 `代码  # 注释` 改成两行时，会删掉那一行「代码 + 注释」，
同时新增一行纯代码。此时应确认 `-` 与 `+` 的代码部分逐字相同。

## 五、按格式的适配要点

### 5.1 JS / CJS / MJS

直接用规范，工具链完整。

**注意**：`.cjs` 常不在 ESLint 的 `files` 覆盖范围内（如 `files: ["**/*.js"]`），
导致 `console` / `process` / `__dirname` 全被报 `no-undef`——这是**既有基线噪声**，
不是你改出来的。做 lint 对照时要按规则统计比对，而非按条数。

### 5.2 Python

- 注释用 `#`，模块头为 `# ！<模块定位>`。
- **docstring 不是注释**，见 §六.3。
- 编码声明（`# -*- coding: utf-8 -*-`）是代码指令，模块头放在它**之后**。
- 检测行尾注释**必须用 `tokenize`**，手写状态机一定会错，见 §六.4。

### 5.3 Shell / YAML / Dockerfile / JSONC

- 用 `#`（JSONC 用 `//`）；`# ！` 模块头置于 shebang（若有）之后。
- 这类文件通常已有不错的注释密度，重点往往是**补模块头**与**清分隔线**。
- JSONC 虽是 JSON 超集，但注释能力是它存在的理由，可放心加注释。

## 六、踩过的坑（按发现顺序）

### 6.1 整体重写会静默改动"非注释"内容

**现象**：重写 239 行的文件后，diff 里出现大量与注释无关的变更行。
**根因**：原文件大量空白行带缩进（如 4 个空格），编辑器写入时被规范化。
**对策**：改用**按行号定位的整段替换**；只替换注释行/注释段，代码行一个字节都不经过。
需要新增注释时用插入，不做全文件生成。

### 6.2 末尾换行被批量改动（19 个文件）

**现象**：全范围复核时发现 19 个已提交文件相对基线多了末尾换行。
**根因**：早期批次尚未内置末尾换行校正，重写时统一补了 `\n`。
**对策**：① 改写后逐文件比对基线最后一个字节；② 已提交的要回头修正并单独提交说明
（本例 `a215af3`），不要藏在后续提交里。

**教训**：这类改动**通过 token 等价校验**（它不看空白），只有专项比对才能发现。
所以 §四.2 的三项核对不可省。

### 6.3 Python docstring 是代码，不是注释

**现象**：差点按"禁止块注释"的规则把 157 处 docstring 改成 `#`。
**根因**：JS 的 `/** */` 是纯注释，改 `//` 无副作用；Python 的 docstring 是**字符串字面量**，
可通过 `__doc__` 在运行时读取，被 `help()`、IDE 提示、doctest、Sphinx 使用。
改掉等于**真的删掉这些字符串**，属行为变更。
**对策**：**保留全部 docstring**，三层结构改用 `#` 行注释实现，`# ！` 模块头置于 docstring 之前。
约束变为「AST 等价 **且** `__doc__` 可用性不变」，两者都要验证。

### 6.4 docstring 内部的 `#` 会被误判为注释

**现象**：行尾注释检测工具对某文件虚报 8 处，实际只有 1 处。
**根因**：初版用手写的引号状态机逐行扫描，无法识别**跨行字符串**，
把模块 docstring 里的命令行示例（如 `python x.py --model planner   # 测试 Planner`）当成了行尾注释。
**对策**：改用标准库 `tokenize`——先收集出现过真实词法单元的行，
再挑出「同行且之前有代码」的 `COMMENT` 词法单元。修正后复检此前 12 个已提交文件，确认无漏检。

**教训**：**解析代码不要手写词法规则**，用编译器/解释器自带的解析器。

### 6.5 手写字面量处理转义不可靠

**现象**：用「手写字面量 + 断言」改写 `elif ch == "\x1b":  # Esc` 时断言失败。
**根因**：`\\x03` 经 JSON → shell → Python 多层转义被折叠成真正的控制字符。
（断言拦下了写入，文件未受损。）
**对策**：改为**从词法单元取注释文本**（`move_trailing.py`），不经过任何字面量。
实测 `"\x1b"` / `"\x03"` 逐字不变。

### 6.6 行尾注释的唯一例外：工具指令

**现象**：全批次清理后仍余 25 处行尾注释。
**根因**：它们是 `# noqa: BLE001`、`# noqa: F401`、`# type: ignore` 等 **lint 工具指令**，
**必须与代码同行才生效**。
**对策**：保留，并在文档中登记为「不用行尾注释」的合理例外。
工具指令后的理由说明可继续同行；若理由较长，可改为前置注释 + 简短指令。

### 6.7 清分隔线时留下多余空行

**现象**：把「分隔线 / 标题 / 分隔线」三行分别置空后，出现连续三个空行。
**根因**：三段替换为三个空字符串，而非整段压缩。
**对策**：把三行**整段替换为一行**纯标题，而不是逐行清空。改完检查「连续三空行」计数为 0。

### 6.8 BOM 会被静默抹掉

**现象**：侦察时发现 4 个配置文件以 BOM 开头。
**根因**：普通 `utf-8` 写入不带 BOM。
**对策**：读写一律用 `utf-8-sig`（Python），或显式保留 BOM 字节；
并在 diff 中确认首行未显示为"被修改"。

### 6.9 JSON 根本不能有注释

**现象**：方案初期把 `package.json` / `tsconfig.json` 等列入范围。
**根因**：JSON 规范不支持注释。
**对策**：这类文件**从范围中排除**并说明原因——不是"暂不做"，而是"不可做"。
若确有必要承载说明，只能改文件格式（如转 `.jsonc`）或写进相邻文档，那是另一件事。

### 6.10 审查工具会因单个坏文件整批中断

**现象**：全量审查 `backend/` 时整个检查崩溃，拿不到其余文件的结论。
**根因**：工具遇到无法解析的文件（UTF-16 编码的 `check.cjs`）直接抛出。
**对策**：改为「解析失败即跳过并计数」，末尾汇总跳过数量。
**单个坏文件不应掩盖其余文件的结论。**

### 6.11 死配置 / 孤儿文件：标注而非删除

**现象**：发现 3 个无任何引用的孤儿调试脚本，以及 1 个不会被加载的 `.eslintrc.js`。
**对策**：按决策统一为**不删除**，在模块头写明其身份与处置建议，例如：

```js
// ！数据表清单检查（孤儿调试脚本）
// ...
// 全仓无任何引用，保留仅作排查参考：如需清理可整体删除，不影响任何功能。
```

理由：删除文件超出注释工程的范围；标注既防止后来者误当在用代码，又为将来清理留依据。

### 6.12 测试文件：只做减法，不套完整三层

**现象**：若对 46 个测试文件套用完整三层，会产生大量"复述断言"的注释。
**根因**：违反 §1.2「只写为什么」——测试的断言本身即文档，
`it('未登录时返回 401')` 再配一句注释是纯噪声。
**对策**（经确认）：测试文件**只做减法 + 模块头**：

- 清除分隔线与装饰性注释（`// ===== on 和 emit =====` → `// on 和 emit`）
- 行尾注释转前置
- 每个文件补 1 行模块头，说明**测什么 + 前置依赖**
- 不新增函数级说明，不为每个 `it()` 加注释

### 6.13 注释与实现不符（失真注释）

**现象**：多处注释描述的行为与代码实际不符。
**实例**：
- 称"使用明文直接存储"，实际存的是 `bcrypt.hash` 的结果
- 称登录校验在 `routes/auth.cjs`，该文件**已不存在**，实际在 `server.cjs`
- 称"兼容旧的 `.eslintrc.js` 中的 extends 和 rules"，实际并未加载该文件，只是手工抄了规则
**对策**：改写时**逐条核对注释与代码**，失真处按实修正，并在提交信息中单独列出。
这类问题在"只改注释"的任务里极易被顺手沿用，反而固化错误。

### 6.14 工具自身也可能不合规

**现象**：审查工具 `audit.mjs` 自己缺少 `// ！` 模块头，还带 4 处分隔线。
**对策**：**dogfooding**——用工具审自己的工具，一并规范化。
写规范的人自己违规会立刻削弱规范的说服力。

### 6.15 `git diff --name-only` 会漏报

**现象**：刚写完文件后立即用 `git diff --name-only HEAD` 取改动清单，返回为空或不全。
**根因**：git 依赖索引的 stat 缓存，写入后缓存尚未刷新。
**对策**：改用 `git status --porcelain`（会刷新），或对已知文件列表直接显式传参。
**默认不要用 `git diff --name-only` 作为"我刚改了什么"的唯一依据。**

### 6.16 提交信息里的数字要对得上

**现象**：提交信息写"3 个文件"，实际只改了 2 个（另一个随前一提交已落地）。
**对策**：提交前用 `git show --name-only --format="" HEAD` 核对文件清单；
发现不符用 `git commit --amend` 修正。
另：统计中文主题长度要用按字符计数的工具（`wc -m` 在部分区域统计的是**字节**，会虚报 3 倍）。

## 七、决策点清单（遇到就问）

| 场景 | 需要确认的问题 |
|---|---|
| 目标含 docstring | 保留还是转注释？（决定是否允许 `__doc__` 变化） |
| 目标含测试文件 | 完整三层还是只做减法？（决定注释密度） |
| 发现死配置 / 孤儿文件 | 删除、标注，还是仅登记待办？ |
| 目标含 JSON | 直接排除（语法不支持），无需询问 |
| 发现代码缺陷 | 是否本次修复？（建议另开 `fix` 提交） |
| 提交粒度 | 按架构层 / 按目录 / 单次提交？ |

## 九、快速上手清单

新任务开始前，逐项确认：

- [ ] 枚举目标文件，按**格式**判定注释可行性（JSON 直接排除）
- [ ] 筛查 BOM、非 UTF-8、0 字节、生成物
- [ ] 统计分隔线 / 装饰性注释 / 行尾注释的数量与分布
- [ ] 确认关键决策：docstring、测试力度、死文件处置
- [ ] 选取 1 个文件试点，跑通"改写 → 校验 → 提交"全链路
- [ ] 确认校验工具**能报错**（故意改代码应 FAIL）

每个文件改完：

- [ ] 等价校验通过（JS 用 token，Python 用 AST）
- [ ] 末尾换行与基线一致
- [ ] 行尾空白行数与内容一致
- [ ] diff 删除行只有注释（或行尾注释改前置的代码行）
- [ ] 无连续三空行
- [ ] docstring 全部保留且可 `__doc__` 读取（Python）
- [ ] `noqa` 等工具指令保留
- [ ] 注释与实现核对无误（失真注释要改）

每批提交前：

- [ ] 跑测试（本例：`npx vitest run` 436 例 / `pytest my_first_crew` 52 例，均须全绿）
- [ ] lint 对照基线**零新增零消除**
- [ ] 提交信息声明"仅改注释 + 零代码行为变更 + 校验方式"
- [ ] `git show --name-only` 核对文件数与提交信息一致
